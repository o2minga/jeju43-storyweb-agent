# 검수 스킬 ‹감수관›

> ⚠ 실제 실행 시 ③ 지어내기 여부 판정에 사용되는 지침은 `.claude/agents/review-agent.md`입니다(나머지 ①②④⑤⑥은 코드가 직접 판정하므로 해당 없음). 이 파일은 참고용 설계 문서이며, 두 파일의 내용이 다르면 `.claude/agents/*.md`가 우선합니다.

> 상세 설계는 `skills/08-review/spec.md`, 전체 구조는 `AGENT-SPEC.md` 참고. 이 문서는 그 두 문서를 바탕으로 한 실행 지시문이며, **특정 유적지의 실제 내용은 예시로도 포함하지 않는다.**
> ⚠ 이 스킬은 파이프라인의 마지막 안전장치다. 여기서 애매하게 넘어가면 잘못된 결과물이 그대로 함께공에게 전달될 수 있다.

## ① 목표
완성된 결과물을 사람이 최종 확인하기 전에 규칙 준수를 자동으로 점검하고, 근거 추적이 가능한 출처 대장을 만든다. **08은 절대 "애매한 상태"로 끝나지 않는다** — 모든 점검 항목은 아래 4가지 상태 중 하나로 명확히 귀결되어야 한다.

| 상태 | 의미 |
|---|---|
| `pass` | 기계적으로 확인했고 규칙을 지켰음 |
| `fail` | 기계적으로 확인했고 규칙 위반이 발견됨 — 어디서 뭐가 문제인지 구체적으로 기록 |
| `needs_human` | 기계적으로 100% 판단할 수 없어 사람 확인이 필요함(실패로 간주하지 않되, 반드시 사람 확인 목록에 남김) |
| `blocked` | 이 항목을 점검하는 데 필요한 이전 단계 결과물 자체가 없어서 점검을 시작할 수 없음 |

`pass`도 `fail`도 아닌 상태를 그냥 넘기거나 조용히 생략하는 것은 금지한다.

## ② 맥락
시작하자마자 필요한 파일(`01-verify.json`, `02-story.json`, `07-chatbot.json`, `05-assemble.html`)의 존재 여부부터 확인한다. **이 중 하나라도 없으면 전체 검수를 `blocked`로 즉시 종료**하고 사유를 명확히 기록하며, 나머지 점검은 절대 진행하지 않는다 — 부분적으로 점검하고 "일단 통과"처럼 보이는 결과를 내는 것이 가장 위험한 실패 모드이기 때문이다. `03-visual.json`/`04-audio.json`은 있으면 확인하되, 03의 자산이 아직 `status:"ready"`가 아니거나(관리자가 외부 도구로 이미지를 아직 안 만든 반자동 워크플로우 대기 상태) 04가 placeholder면 해당 체크만 `needs_human`으로 표시하고 파이프라인을 막지 않는다. `06-map.html`은 선택 사항이다.

## ③ 범위 (포함 / 제외)
**포함**: 6개 항목 자동 점검, 통과/보류/차단 상태와 걸린 항목을 구체적으로 표시, 출처 대장 문서 생성.
**제외**: 이야기·이미지·페이지 자체의 제작이나 수정 — 문제를 고치는 건 각 스킬 담당이고, 08은 발견만 한다.

## ④ 제약 (자동 점검 6개 항목과 판단 방법)
`skills/08-review/spec.md` 4장에 정의된 방법을 그대로 따른다. ①②④⑥은 방법 자체가 이미
기계적으로 정의돼 있어 **Claude 호출 없이 코드로 직접 판정**하고(05의 html·01/02/07의
JSON을 코드가 직접 대조), ⑤는 spec.md 자신이 "원칙적으로 항상 `needs_human`"이라고
못박아 두었으므로 이 역시 **코드 고정값**이다. **Claude 판단이 실제로 필요한 항목은
③ 지어내기 여부 하나뿐이다** — 의역·우회 서술은 키워드 대조만으로 못 잡기 때문이다.

1. **출처 누락 여부** — 별도로 처리됨(코드 파싱).
2. **`[연출]` 표시 여부** — 별도로 처리됨(코드 파싱, placeholder 단계 판정 포함).
3. **지어내기 여부** — `forbidden_topics` 핵심 문구의 키워드 대조로 1차 스크리닝. 키워드가 발견되면 `fail`, 안 보여도 서술이 구체적인 구간이 있으면 `needs_human` — 이 항목은 절대 `pass`만으로 끝내지 않는다.
4. **사실 일치 여부** — 별도로 처리됨(코드 파싱).
5. **용어 풀이 여부** — 별도로 처리됨(항상 `needs_human` 고정값).
6. **AI 챗봇 지식베이스 일치 여부** — 별도로 처리됨(코드 파싱).

그 외 제약:
- `pass`/`fail`/`needs_human`/`blocked` 외의 값은 사용하지 않는다.
- **`needs_human`이 하나라도 있으면 전체 결과는 자동으로 보류(HOLD)다** — `PASS`로 표시하지 않는다.
- 필수 파일 누락(`blocked`)이 있으면 나머지 항목은 실행하지 않고 결과를 `실행불가`로 명확히 표시한다.
- 같은 입력으로 다시 실행하면 항상 같은 결과가 나와야 한다(재현 가능성).

## ⑤ 출력 형식
`skills/08-review/spec.md` 6·7장에 정의된 3종 산출물을 그대로 따른다.

1. **`review_result.json`** — 기계가 읽는 결과. `location_id`, `overall_status`(`PASS`|`HOLD`|`실행불가`), `checks[]`(각 항목의 `check_id`/`name`/`status`/`issues`), `missing_required_files`, `generated_at`.
2. **`source-ledger.md`** — 출처 대장. 포함: 카드/검색 출처의 `verified_facts`, 실제 문헌 이미지(`data-origin="archive"`). **제외**: AI 생성 이미지·영상·오디오(`data-origin="ai"` 또는 `class="ai-generated"`) — 이건 웹 안 `[연출]` 표시로만 관리. 내용/출처/사용 위치 중 하나라도 비면 대장에서 제외하고 "출처 정보 불완전 항목"으로 별도 남긴다(조용히 누락시키지 않는다).
3. **`review-summary.md`** — 사람 최종 확인용 요약. 전체 상태, 자동 통과 항목, 사람 확인 필요 항목, 규칙 위반 발견 항목, 다음 단계.

## ⑥ 성공 기준
`skills/08-review/spec.md` 8장의 체크리스트를 그대로 따른다. 특히 아래는 항상 확인한다.
- 필수 파일이 하나라도 없으면 즉시 `실행불가`로 표시되고 부분 점검 결과가 나오지 않는다.
- 6개 항목 모두 `pass`/`fail`/`needs_human`/`blocked` 중 하나로 명시적으로 귀결된다.
- `needs_human`이 하나라도 있으면 `overall_status`가 절대 `PASS`가 아니다.
- `fail` 항목은 전부 구체적 위치와 함께 기록된다.
- 출처 대장에 AI 생성 이미지·영상·오디오가 하나도 섞이지 않는다.
- 같은 입력으로 다시 실행해도 동일한 결과가 나온다(재현성).
- **이 스킬을 다른 유적지의 산출물로 실행해도 동일한 기준을 만족한다.**

## 공통 규칙 (모든 스킬 공통)
1. **출처 표기 필수** — 카드 밖 자료도 가능하나 출처 명시. 개인 블로그·유튜브 금지
2. **쉬운 언어** — 청소년·외국인이 배경지식 없이 읽을 수 있게
3. **사실 vs 연출 구분** — AI 생성 이미지·영상엔 `[연출]` 표시
4. **지어내기 금지** — 카드에 없는 내용은 채우지 않음
5. **충돌 시 병기** — 수치·날짜가 자료마다 다르면 '기록마다 다름'으로 나란히 표기

- 출력 예시: `output/gwandeokjeong/review_result.json`, `source-ledger.md`, `review-summary.md` (아직 미작성 — 05 완료 후 실행 가능)
